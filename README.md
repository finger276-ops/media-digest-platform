# Платформа дайджестов

Это отдельная мультипроектная версия дашборда. Она не использует старые таблицы `dashboard_*` и не смешивает данные с текущим проектом «Дайджест водительских чатов».

## Что уже реализовано

- отдельные таблицы Supabase с префиксом `platform_*`;
- создание нескольких проектов;
- отдельные периоды, файлы, сообщения и инфоповоды внутри каждого проекта;
- доступ через коды проекта:
  - код просмотра;
  - код редактора;
- отдельный пароль владельца платформы;
- загрузка CSV/Excel:
  - Медиалогия CSV/Excel;
  - Brand Analytics CSV/Excel, включая теговые колонки после `Обработано`;
  - универсальный CSV/Excel;
- саммари по выбранным периодам;
- ручное редактирование саммари;
- динамика сообщений и негатива по периодам;
- история периодов с редактированием названия, дат, файла и статуса;
- мультипроектная ручная модерация инфоповодов:
  - ручное создание инфоповода;
  - редактирование названия, описания и тегов;
  - объединение инфоповодов;
  - перенос сообщений между инфоповодами;
  - отметка «нерелевант» для сообщения внутри темы;
  - скрытие сообщений и инфоповодов.

## Как развернуть отдельно от текущего проекта

Создай новый GitHub-репозиторий, например:

```text
media-digest-platform
```

Загрузи туда содержимое этой папки.

В Streamlit Cloud укажи главный файл:

```text
streamlit_app.py
```

## SQL в Supabase

В Supabase открой:

```text
SQL Editor → New query
```

Вставь и выполни содержимое файла:

```text
sql/platform_schema.sql
```

Будут созданы таблицы:

```text
platform_projects
platform_periods
platform_table_rows
platform_manual_rows
platform_project_members
```

Они не пересекаются со старыми таблицами `dashboard_periods`, `dashboard_table_rows`, `dashboard_manual_rows`.

## Secrets в Streamlit Cloud

В настройках приложения добавь:

```toml
SUPABASE_URL = "https://xxxxxxxx.supabase.co"
SUPABASE_SERVICE_ROLE_KEY = "твой_service_role_key"
SUPABASE_STORAGE_BUCKET = "dashboard-csv"
PLATFORM_ADMIN_PASSWORD = "придумай_пароль_владельца"
```

`SUPABASE_STORAGE_BUCKET` можно использовать тот же, потому что файлы платформы сохраняются по пути:

```text
project_id/period_id/file.csv
```

Но для полной изоляции можно создать отдельный bucket, например:

```toml
SUPABASE_STORAGE_BUCKET = "digest-platform-files"
```

### Уведомления об ошибках (необязательно)

Падение раздела заказчик видит как вежливое сообщение, а владелец без
настройки — только в логах контейнера. Чтобы узнавать о сбоях сразу, добавь
один из каналов (или оба):

```toml
ALERT_WEBHOOK_URL = "https://hooks.example/alert"  # POST с JSON о сбое
SENTRY_DSN = "https://key@sentry.example/1"        # нужен пакет sentry-sdk
```

Повторы одного и того же сбоя глушатся (не чаще раза в 10 минут), ошибки
доставки не роняют страницу. Без настройки поведение прежнее — только лог.

## Роли доступа

### Владелец платформы

Входит по `PLATFORM_ADMIN_PASSWORD`. Может:

- создавать проекты;
- редактировать проекты;
- видеть все проекты;
- загружать файлы в любой проект;
- редактировать периоды и саммари.

### Редактор проекта

Входит по коду редактора конкретного проекта. Может:

- загружать файлы;
- редактировать периоды;
- редактировать саммари.

### Просмотр проекта

Входит по коду просмотра. Может:

- смотреть саммари;
- смотреть динамику;
- смотреть инфоповоды и сообщения.

## Первый запуск

1. Войти как владелец платформы.
2. Открыть раздел **Проекты**.
3. Создать проект.
4. Указать код просмотра и код редактора.
5. Перейти в **Загрузка файла**.
6. Загрузить CSV или Excel.
7. После обработки открыть **Дашборд**.

## Как не смешивать данные с текущим дашбордом

Текущий проект использует таблицы:

```text
dashboard_*
```

Платформа использует таблицы:

```text
platform_*
```

Даже если оба приложения подключены к одному Supabase-проекту, данные лежат в разных таблицах.

Для максимальной изоляции можно создать отдельный Supabase-проект только под платформу.


## Специфика Brand Analytics

В выгрузках Brand Analytics после служебной колонки `Обработано` обычно идут теговые колонки системы. Например: `ТЕХНОНИКОЛЬ`, `Теплоизоляция`, `КП`, `Knauf Insulation`, `Маркетплейсы`, `ROCKWOOL`, `PR`, `отзыв` и т.д.

Платформа сохраняет эти колонки при импорте и использует их как первичные сигналы для формирования тегов, тем, инфоповодов и аналитики. Это важно для бренд-мониторинга: тема должна собираться не только по словам из текста, но и по разметке Brand Analytics.


### Удаление выгрузок

В истории периодов доступна кнопка удаления выгрузки. Удаление выполняется безопасно: строки `platform_table_rows` удаляются небольшими пакетами, чтобы большие выгрузки не падали на PostgREST/Supabase timeout. Если Supabase не разрешит физическое удаление, период будет скрыт из интерфейса, а приложение покажет предупреждение вместо аварийного падения.

## Обновление 3.2: универсальные темы проектов

Платформа больше не использует такси-словарь как базовый профиль. Алгоритм обработки теперь строит темы и теги в первую очередь из самой выгрузки:

- `Сюжет`;
- `Теги`;
- `Категории`;

Такси-правила сохранены только как legacy-профиль для старых проектов с водительскими чатами. Для новых проектов по умолчанию используется универсальный профиль.

Также исправлен импорт Excel:

## Логика Brand Analytics: сюжеты и теги

Для выгрузок Brand Analytics действует отдельное правило:

- **Инфоповоды формируются по колонке `Сюжет`**. Один сюжет = один инфоповод. Теги и текстовые ключевые слова не создают отдельные инфоповоды.
- **Теги формируются из колонок после служебной колонки `Обработано`**. Если в такой колонке есть значение, сообщение получает соответствующий тег.
- Теговые колонки используются для аналитики, фильтрации и просмотра сообщений по тегу, но не смешиваются с логикой инфоповодов.
- На главной странице дашборда показывается статистика тегов: количество сообщений, суммарные просмотры и вовлеченность.
- Под таблицей инфоповодов есть интерактивный блок тегов: при выборе тега открываются все сообщения с этим тегом.

Такой подход нужен, потому что в Brand Analytics `Сюжет` отражает тематическую группировку публикаций, а блок колонок после `Обработано` — это отдельная система тегов.

## Версия 3.5: удаление выгрузок

В разделе **История периодов** для редактора/владельца добавлена опасная зона **«Удалить выгрузку без восстановления»**.

Удаление выгрузки:

- удаляет запись периода из `platform_periods`;
- удаляет все обработанные строки этого периода из `platform_table_rows`;
- удаляет ручные правки, которые явно ссылаются на этот период/его инфоповоды;
- по возможности удаляет исходный файл из Supabase Storage;
- не затрагивает другие проекты и другие периоды.

Подтверждение словом `УДАЛИТЬ` убрано: удаление выполняется одной кнопкой в опасной зоне.

## Версия 3.6: стартовая страница Brand Analytics

Для выгрузок Brand Analytics действует отдельная логика:

- **инфоповоды** строятся только по колонке `Сюжет`;
- **теги** строятся только из колонок, которые идут после служебной колонки `Обработано`;
- теги не создают инфоповоды и не подмешиваются в список сюжетов;
- старые такси-метки и универсальные авто-темы не должны отображаться в блоке тегов Brand Analytics.

Стартовая страница проекта содержит:

1. название проекта;
2. блок статистики: количество сообщений, суммарная аудитория/просмотры, суммарная вовлеченность;
3. саммари;
4. блок тегов со статистикой по сообщениям, просмотрам и вовлеченности;
5. блок инфоповодов по сюжетам;
6. блок ключевых сообщений с переключением на всю ленту.

Ключевые сообщения — это топ-15 сообщений с максимальной вовлеченностью. Если вовлеченность равна 0, дополнительным критерием выступает аудитория/просмотры.


## Исправление метрик Brand Analytics

Для выгрузок Brand Analytics:
- `audience` берется из колонки `Аудитория`;
- `views` / охват берется из колонок `Просмотры` или `Просмотров`;
- пустые и нечисловые значения считаются как `0`;
- числа с пробелами, неразрывными пробелами и служебными символами корректно приводятся к числу.

После обновления файлов `src/preprocess.py` и `src/import_adapters.py` старые выгрузки, обработанные предыдущей версией, нужно удалить и загрузить заново, чтобы в `platform_table_rows` появились корректные `audience` и `views`.

## Версия 4.0: интеграция дашборда водительских чатов

Платформа поддерживает два независимых типа проектов внутри единой мультипроектной архитектуры:

1. **Обычные проекты мониторинга / Brand Analytics**
   - данные хранятся в `platform_*`;
   - теги Brand Analytics берутся из колонок после `Обработано`;
   - инфоповоды Brand Analytics строятся по колонке `Сюжет`;
   - на главной странице показываются статистика, саммари, теги, инфоповоды и ключевые сообщения.

2. **Проекты “Дайджест водительских чатов”**
   - создаются отдельным проектом с профилем `Дайджест водительских чатов`;
   - также используют только таблицы `platform_*`, без обращения к старым `dashboard_*`;
   - сохраняют изоляцию проектов, периодов и ручных правок;
   - получают отдельный экран с такси-метриками, саммари, уровнями сборки инфоповодов, инфоповодами водительских чатов, ключевыми сообщениями и динамикой.

### Как создать проект водительских чатов

1. Войти как владелец платформы.
2. Открыть раздел **Проекты**.
3. Создать новый проект.
4. В поле **Профиль алгоритма** выбрать **Дайджест водительских чатов**.
5. Загрузить выгрузку водительских чатов через раздел **Загрузка файла**.
6. Открыть **Дашборд**.

### Важно

Интеграция не смешивает данные старого дашборда и мультиплатформы. Старый дашборд использует `dashboard_*`, мультиплатформа использует только `platform_*`. Профиль водительских чатов в платформе работает как отдельный тип проекта, но хранит данные внутри общей мультипроектной схемы.

## Фильтр малых инфоповодов

В версии 4.1.1 добавлен общий фильтр малых инфоповодов. Он нужен для проектов, где инфоповоды формируются алгоритмически и могут появляться одиночные шумовые темы на 1–3 сообщения.

В боковой панели дашборда доступен параметр:

```text
Мин. сообщений в инфоповоде
```

По умолчанию для алгоритмических проектов и профиля «Дайджест водительских чатов» скрываются инфоповоды, где меньше 4 сообщений. Для Brand Analytics-сюжетов по умолчанию сохраняются все сюжеты, потому что они приходят из исходной редакционной разметки системы.

Фильтр не удаляет сообщения и не меняет исходные данные: малые инфоповоды скрываются только из таблицы инфоповодов и саммари, а сообщения остаются в общей статистике и полной ленте.

## Версия 4.1.3 — последовательное сравнение при выборе двух и более периодов

Если на главном экране выбрано два или больше периодов, верхний блок строит не суммарную статистику, а последовательное сравнение по периодам.

Периоды сортируются в хронологическом порядке и сравниваются цепочкой:

```text
период 1 → период 2 → период 3 → ...
```

В верхних карточках показывается последний выбранный период и изменение относительно предыдущего периода. В сравнительной таблице отображается каждый период и изменение к предыдущему по метрикам:

- сообщения;
- аудитория;
- охват;
- вовлеченность;
- позитив;
- нейтрал;
- негатив.

Для числовых метрик показывается изменение в абсолютных значениях и процентах. Для тональности показывается изменение в процентных пунктах. Если выбран один период, платформа показывает обычную статистику по этому периоду.

## Версия 4.3 — оптимизация загрузки и отображения

В этой версии ускорена работа дашборда без изменения пользовательской логики:

- загрузка таблиц из Supabase кешируется на уровне Streamlit;
- периоды, проекты и ручные правки также кешируются и сбрасываются после изменений;
- `platform_table_rows` загружается пакетно по нескольким периодам, а не период за периодом;
- из Supabase для обработанных таблиц запрашиваются только нужные поля `period_id,payload`;
- префиксация ID для нескольких периодов переведена с `DataFrame.apply()` на более быстрые операции;
- сообщения получают предрасчитанные технические колонки `_audience`, `_reach`, `_engagement`, `_sentiment_lower`, `_is_negative_bool`;
- тяжелые функции `enrich_messages`, `apply_manual_overrides`, `aggregate_events`, `build_tag_statistics` кешируются;
- добавлены дополнительные индексы в `sql/platform_schema.sql` для ускорения выборок по проекту, периоду и таблице.

Если база уже создана, достаточно выполнить новые `create index if not exists ...` из `sql/platform_schema.sql` в Supabase SQL Editor.

## v4.3.5 — оптимизация кеша и диагностика скорости

В версии 4.3.5 добавлен отдельный слой `src/services/cached_store.py`, который оборачивает операции `platform_store` и кеширует чтение проектов, периодов, ручных правок и обработанных таблиц. Вместо глобального `st.cache_data.clear()` после каждого изменения используется версионирование кеша по проекту: правки в одном проекте не сбрасывают кеши других проектов.

Также добавлен модуль `src/services/perf.py` для замера времени ключевых операций. Для владельца платформы в боковом меню доступен переключатель **«Диагностика скорости»**. Он показывает последние операции загрузки и подготовки данных с временем выполнения в миллисекундах.

Изменения не требуют миграции Supabase и не меняют бизнес-логику платформы.

## Версия 4.6.0 — автозагрузка выгрузок через n8n

Выгрузки Brand Analytics больше не обязательно загружать руками. Появился путь
«письмо с отчетом BA → n8n → Supabase → период в платформе».

Схема:

```text
Brand Analytics → письмо с Excel → n8n кладет файл в Storage
и ставит задачу в platform_ingest_queue → воркер платформы обрабатывает файл
штатным пайплайном и создает период проекта
```

n8n не обрабатывает данные — он только доставляет файл. Вся логика остается в
платформе (`src/services/ingest.py`), поэтому правила Brand Analytics (инфоповоды
по колонке `Сюжет`, теги из колонок после `Обработано`, метрики «Аудитория» и
«Просмотры») работают одинаково при ручной и автоматической загрузке.

Что добавлено:

- `sql/platform_ingest_schema.sql` — таблицы `platform_ingest_queue` и
  `platform_ingest_sources` (выполнить один раз в Supabase SQL Editor);
- `src/services/ingest.py` — headless-пайплайн импорта, общий для интерфейса и воркера;
- `src/services/ingest_queue.py` — очередь: постановка, атомарный захват задач,
  ретраи, возврат зависших задач;
- `scripts/ingest_worker.py` — воркер, запускается по расписанию или вручную;
- `src/ingest_admin_ui.py` — раздел **Автозагрузка** в интерфейсе;
- `.github/workflows/ingest-worker.yml` — запуск воркера каждые 15 минут;
- `n8n/brand-analytics-email-ingest.json` — готовый workflow для импорта в n8n;
- `n8n/docker-compose.yml` — self-hosted n8n;
- `requirements-worker.txt` — зависимости воркера без Streamlit;
- `tests/` — тесты очереди, воркера и интерфейса без обращения к сети.

Раздел **Автозагрузка** (доступен редактору и владельцу) показывает очередь со
статусами, тексты ошибок, кнопки «Повторить» и «Удалить», а также позволяет
обработать очередь прямо из интерфейса, не дожидаясь планового запуска воркера.
Там же настраиваются источники: ключ источника из n8n привязывается к проекту и
параметрам алгоритма, поэтому новые проекты добавляются без правок в n8n.

Защита от дублей двойная: уникальный индекс по SHA-256 файла не дает поставить в
очередь одно и то же письмо дважды, а период, названный автоматически по датам
сообщений, при повторной обработке перезаписывается, а не дублируется.

Полная инструкция по развертыванию — `docs/AUTOMATION.md`.

## Версия 4.11.0 — инфоповоды собираются по смыслу, а не по точной строке

### Что было не так

Инфоповоды собирались по точному совпадению заголовка:
`df["group_key"] = df["title"].str.lower().str.strip()`. Внутри одного периода
для Brand Analytics это работало: заголовок — это «Сюжет», то есть готовая
группировка самого источника. Разваливалось в двух местах:

- **Между периодами.** При загрузке `event_id` получает префикс периода
  (`_prefix_ids` в `src/platform_store.py`), поэтому апрельский и майский сюжет
  связывает только текст заголовка. Brand Analytics переформулирует сюжеты, и
  одна тема разъезжается на два инфоповода с разной динамикой.
- **В алгоритмических проектах**, где заголовок собирается из ключевых слов:
  другой порядок слов — другой инфоповод.

### Что сделано

**Ступень 1 — нормализация (всегда включена).** `normalize_event_title`
приводит заголовок к сравнимой форме: регистр, ё/е, кавычки всех начертаний,
тире, многоточия, пробелы внутри чисел («1 000» → «1000»), пунктуация. Тут
склеивается только то, что и так было одним сюжетом.

**Ступень 2 — смысловая склейка (настраивается).** Близкие заголовки сводятся к
одному лидеру по взвешенной мере Жаккара с IDF и лёгким стеммингом, поэтому
«ТЕХНОНИКОЛЬ открыла завод…» и «Открытие завода ТЕХНОНИКОЛЬ…» становятся одним
инфоповодом. Склейка идёт **к лидеру, а не по цепочке**: каждый участник похож
непосредственно на самую крупную тему группы, поэтому A~B и B~C не превращают
A и C в один инфоповод.

Порог выбирается в «⚙️ Вид» → «Склейка похожих заголовков»: «Выключено»,
«Осторожно» (0,75), «Обычно» (0,62), «Агрессивно» (0,5). Значение сохраняется в
настройках проекта вместе со стартовым разделом.

### Каждое решение видно и отменяемо

- Над таблицей инфоповодов — блок «Склеено похожих заголовков: N», где видно,
  какие формулировки собраны под каким сюжетом.
- Кнопка «Не склеивать» рядом с вариантом выводит заголовок из автосклейки
  навсегда (ручная запись `title_merge_blocks`); вернуть — в блоке «Заголовки
  без автосклейки».
- В таблице рядом с сюжетом стоит «(+2)» — столько формулировок под ним лежит.
- Кнопка «Проверить, сколько заголовков дублируется» считает на текущих данных,
  сколько инфоповодов останется при каждом пороге. Вопрос «это реальная
  проблема или нет» решается измерением на своей выгрузке.

### Порядок операций

Склейка идёт **до** порога «мин. сообщений в инфоповоде»: иначе одна тема,
разбитая источником на три формулировки по два сообщения, отсекалась бы как
мелочь, хотя вместе это шесть сообщений.

### Обработка выгрузки

`event_id` сюжета Brand Analytics теперь считается от нормализованной формы
заголовка, поэтому разные написания одного сюжета получают один идентификатор
ещё при загрузке. Название инфоповода остаётся исходным — берётся та
формулировка, за которой больше сообщений. Ранее загруженные периоды не
пересчитываются.

### Настройка склейки — консервативная

- Заголовки короче трёх значимых слов склеиваются только при точном совпадении
  нормализованной формы: у «Пожар на складе» слишком мало сигнала.
- Нужно минимум два общих значимых слова.
- IDF гасит вес слов, которые есть в каждом заголовке (например, названия
  бренда), поэтому общий бренд сам по себе не повод объединить две темы.
- Отдельное правило для усечённых заголовков: если короткий почти целиком
  содержится в длинном, это одна тема.

Ложная склейка считается дороже пропуска: на контрольном наборе разные события
с общим брендом не объединяются ни при одном из предлагаемых порогов.

### Производительность

`merge_similar_events` кэшируется по дешёвым ключам (проект, периоды, версии
данных, порог, список исключений) — сам DataFrame в ключ кэша не попадает.
Сравнение идёт по инвертированному индексу слов, а не «каждый с каждым»:
2 169 уникальных заголовков обрабатываются за 1,4 с и затем берутся из кэша.

Код: `src/services/event_titles.py`, тесты: `tests/test_event_titles.py`.

## Версия 4.12.0 — тексты, написанные моделью

Платформа умеет генерировать **саммари периода**, **комментарий к индексам
бренда** и **блок рисков для клиента**. Доступ — только у владельца платформы:
генерация тратит деньги и отправляет данные проекта внешнему сервису, поэтому
кнопка не должна попадаться ни клиенту, ни редактору проекта.

### Платформа считает, модель интерпретирует

Модель не считает ничего. Все числа — сообщения, тональность, динамика к
предыдущему периоду, доли негатива по темам, индексы бренда — платформа уже
посчитала и складывает в короткую карточку данных. Модель получает карточку и
объясняет, что эти числа значат. Ошибиться в арифметике она не может, потому что
не умножает и не делит, а системный промпт прямо запрещает использовать числа,
которых в карточке нет.

Что именно уходит в запрос, видно до нажатия кнопки: в панели есть блок «Что
именно уходит в модель» с полным текстом и оценкой размера в токенах.

### Провайдеры — российские

| Провайдер | `AI_PROVIDER` | Ключи |
| --- | --- | --- |
| YandexGPT | `yandex` | `YANDEX_API_KEY`, `YANDEX_FOLDER_ID` |
| GigaChat | `gigachat` | `GIGACHAT_AUTH_KEY` |

Оба доступны с российского сервера без прокси и принимают оплату в рублях, а
данные не покидают РФ. Для бренд-мониторинга клиентов это важнее разницы в
качестве текста. Провайдер выбирается одной строкой в Streamlit Secrets; если
ключей нет, панель показывает, чего не хватает, и ничего не ломается.

### Где появляются тексты

| Текст | Раздел |
| --- | --- |
| Саммари периода | «Отчёт»; кнопка «Сделать саммари периода» подставляет его в основное саммари — тогда он попадает в Word, PDF и PNG |
| Комментарий к индексам | «Индексы бренда», под карточками |
| Блок рисков | «Обзор», первым блоком |

Текст всегда проходит через аналитика: после генерации он открывается в поле
для правки и сохраняется отдельной кнопкой. Под сохранённым текстом стоит
подпись, что он сгенерирован моделью и проверен — клиент имеет право это знать.

### Выдержки сообщений — по галочке

По умолчанию в запрос попадают до 24 выдержек из самых заметных сообщений (для
блока рисков — только из негативных), по 400 символов. Галочку можно снять:
тогда модель видит только цифры и заголовки, а тексты сообщений не покидают
платформу вообще. Саммари получается суше, но для проектов с чувствительным
содержанием это правильный режим.

### Что добавлено

- `src/services/ai_provider.py` — транспорт: конфиг из секретов, OAuth GigaChat
  с кэшем токена и одним повтором при протухании, понятные русские ошибки
  вместо трассировок;
- `src/services/ai_summary.py` — сборка карточки данных и три промпта;
- `src/ai_summary_ui.py` — панель «Тексты от ИИ» в разделе «Отчёт»;
- `tests/test_ai_summary.py` — 47 проверок на поддельном транспорте, без сети:
  формат запроса к обоим провайдерам, разбор ответа, повтор при истёкшем токене,
  расшифровка ошибок 401/429/500, состав карточки данных;
- `docs/AI.md` — настройка, стоимость запроса и что проверять в тексте перед
  сохранением.

Отдельной схемы SQL не нужно: тексты лежат в `platform_manual_rows` рядом с
остальной ручной правкой, по одному на набор периодов, вместе с провайдером,
моделью и временем генерации.

## Версия 4.12.1 — владелец может открыть генерацию редакторам

Генерация текстов по-прежнему закрыта по умолчанию, но теперь это настройка, а
не жёсткое правило. В панели «Тексты от ИИ» у владельца платформы появился
переключатель **«Кому доступна генерация в этом проекте»**:

| Значение | Кто видит панель |
| --- | --- |
| Только владелец платформы (по умолчанию) | вход по `PLATFORM_ADMIN_PASSWORD` |
| Владелец и редакторы проекта | плюс вход по коду редактора этого проекта |

Настройка хранится в `platform_projects.settings.ai_access` и действует только в
своём проекте: открыв доступ в одном, вы не открываете его в остальных.
Переключатель видит только владелец — редактор не может расширить доступ сам.

Три решения, принятые осознанно:

- **Клиент (роль «просмотр») генерацию не получает ни при каком значении.** Он
  ничего не редактирует, а каждая кнопка стоит платного запроса к модели;
  сохранённые тексты он видит как обычно.
- **Незнакомое значение в настройках трактуется как «только владелец».**
  Расширение доступа должно быть явным решением, а не следствием опечатки.
- **Доступ настраивается независимо от ключей провайдера.** Владелец может
  открыть его редакторам заранее, а ключи добавить позже — и наоборот.

Редактору, которому доступ открыли, панель показывает напоминание, что каждый
запуск платный. Ключи и настройки провайдера ему не видны.

Логика доступа лежит в `src/services/ai_summary.py` (`ai_access_level`,
`can_generate_ai`) — отдельно от интерфейса, поэтому проверяется тестами без
запуска Streamlit.

## Версия 4.12.2 — GigaChat и сертификаты НУЦ Минцифры

Первое же обращение к GigaChat падало так:

```
CERTIFICATE_VERIFY_FAILED: self-signed certificate in certificate chain
```

Это не ошибка ключа и не сбой сети: GigaChat отдаёт TLS-сертификат, подписанный
Национальным удостоверяющим центром Минцифры, а этого корня нет в системных
хранилищах — ни на Streamlit Cloud, ни в свежей Ubuntu.

### Как это решено

Сертификат кладётся в папку `certs/` в корне репозитория, и платформа находит
его сама:

```bash
mkdir -p certs
curl -sS -w '\n' https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt \
  > certs/russian_trusted_ca.pem
curl -sS -w '\n' https://gu-st.ru/content/lending/russian_trusted_sub_ca_pem.crt \
  >> certs/russian_trusted_ca.pem
```

Нужны **оба** сертификата: без выпускающего цепочка не соберётся. Файл
коммитится в репозиторий — это публичный корневой сертификат, а не секрет.

Важно, как именно он применяется: сертификат передаётся в `verify=` **только
для запросов к GigaChat** и не попадает в системный список доверенных корней.
Остальные соединения платформы проверяются как раньше. Это принципиально
безопаснее, чем и общая установка корня в систему, и отключение проверки.

Если файл уже лежит на сервере, путь задаётся секретом `GIGACHAT_CA_BUNDLE`.

### Ошибка теперь объясняет себя

Вместо трассировки `HTTPSConnectionPool(host='ngw.devices.sberbank.ru'...)`
панель показывает, что произошло, куда положить файл и какой командой его
скачать. Если путь к сертификату задан, но не подошёл, в сообщении стоит именно
этот путь — чтобы не гадать, какой файл читается.

`GIGACHAT_VERIFY_SSL = "false"` остаётся крайней мерой. Когда проверка
выключена, в строке состояния панели прямо написано «проверка сертификата
ВЫКЛЮЧЕНА» — чтобы временная мера не превратилась в постоянную незаметно.

### Кнопка «Проверить подключение»

В панели «Тексты от ИИ» у владельца платформы. Один короткий запрос к модели:
либо её ответ, либо причина отказа. Проверять настройку на первом реальном
саммари больше не нужно.

Тесты: `tests/test_ai_summary.py` воспроизводит падение по сертификату на
поддельном транспорте и проверяет, что путь к файлу доезжает до запроса при
всех трёх режимах — файл задан, файла нет, проверка выключена.

## Версия 4.12.4 — сертификат GigaChat заводится без терминала

Версия 4.12.2 научила платформу пользоваться сертификатом НУЦ Минцифры, но
предполагала, что у администратора есть терминал: команда с `curl`, коммит,
пуш. На Streamlit Cloud терминала нет, а два скачанных файла надо ещё и
склеить в правильном порядке — шаг, на котором всё и останавливалось.

### Помощник в интерфейсе

В панели «Тексты от ИИ» появился блок **«Сертификат для GigaChat: собрать без
терминала»**. Он виден владельцу платформы, пока сертификат не настроен, и
исчезает, когда настроен.

1. Скачать с gosuslugi.ru/crt два файла **для Linux, в формате `.crt`** —
   корневой и выпускающий.
2. Загрузить оба в блок.
3. Скопировать готовый блок в Streamlit Secrets.

Платформа не просто склеивает файлы, а проверяет их: что это PEM, что это
сертификаты удостоверяющего центра, что срок действия не истёк, и что их
действительно два. Если скачан `.cer` для Windows вместо `.crt` для Linux —
об этом будет сказано сразу, а не через непонятную ошибку TLS.

### Новый способ хранения

```toml
GIGACHAT_CA_PEM = """
-----BEGIN CERTIFICATE-----
...
"""
```

Сертификат живёт в секретах, а не в репозитории, и переживает передеплой.
При старте платформа сохраняет его во временный файл (один раз на содержимое)
и передаёт путь в `verify=` — только для запросов к GigaChat.

Порядок приоритетов: `GIGACHAT_CA_PEM` (текст в секретах) → `GIGACHAT_CA_BUNDLE`
(путь к файлу) → файл в папке `certs/`. Оба прежних способа работают как
раньше.

### Сообщение об ошибке стало двухдорожечным

Текст про неудачную проверку сертификата теперь начинается с варианта «без
терминала» и только потом предлагает команду с `curl` — чтобы человек без
доступа к консоли не упирался в инструкцию, которую не может выполнить.
