## 1. Сделать владельцу платформы

### 1.1. Секреты GitHub — срочно: ночные резервные копии не делаются

Ночная резервная копия работает в GitHub Actions. У GitHub свои секреты,
отдельные от Streamlit Cloud. Пока их нет, задача падает, и копия данных сама
не создаётся.

- [ ] Сразу, до настройки: страница «Проекты» → блок «Резервные копии» →
      **«Сделать копию сейчас»**. Эта кнопка работает без секретов GitHub.
- [ ] GitHub → репозиторий → **Settings** → **Secrets and variables** →
      **Actions** → **New repository secret**. Добавить:
  - `SUPABASE_URL`
  - `SUPABASE_SERVICE_ROLE_KEY`
  - `SUPABASE_STORAGE_BUCKET` — только если он задан в секретах Streamlit.

  Значения — те же, что в Streamlit Cloud → приложение → **Settings** →
  **Secrets**, или в Supabase → **Project Settings** → **API**. Ключ
  `service_role` вводится только в это поле. Не вставляйте его в код, файлы
  репозитория или переписку.
- [ ] **Actions** → «Резервная копия» → **Run workflow**. Запуск должен
      стать зелёным, а в нём должен появиться файл `platform-backup-…`.

Подробнее: `docs/BACKUPS.md`, раздел «Секреты GitHub».

### 1.2. Миграции базы в Supabase

Без миграции 0007 правки сохраняются, но раздел «Платформа → Журнал» пуст:
не видно, кто и что менял.

- [ ] Supabase → **SQL Editor** → **New query**. Проверить, что применено:
  ```sql
  select version, name, applied_at from public.schema_migrations order by version;
  ```
- [ ] Если в списке нет `0007` — выполнить `sql/migrations/0007_platform_audit_log.sql`.
- [ ] Если нет `0006` — выполнить `sql/migrations/0006_platform_sessions_schema.sql`.
      Без неё раздел «Платформа → Сессии» молча не показывает, кто сейчас
      в платформе.

Файлы можно выполнять повторно, это безопасно. Подробнее:
`sql/migrations/README.md`.

### 1.3. Прислать цифры скорости

Время на загрузку кода платформы уже замерено: около 1,2 с, один раз при
старте сервера. Повседневную скорость определяют ответы Supabase и расчёты на
странице. Их можно замерить только на боевой платформе.

- [ ] Войти владельцем. Внизу боковой панели включить **«Диагностика скорости»**.
- [ ] Открыть раздел, который открывается медленно. Прислать Claude:
  - цифры из боковой панели;
  - название раздела;
  - сколько сообщений в выбранном периоде.

### 1.4. Раз в пару месяцев

- [ ] Заглянуть в GitHub → **Actions**. GitHub сам выключает расписание в
      репозитории, где 60 дней не было изменений. Если «Резервная копия»
      выключена — нажать **Enable workflow**. Блок «Резервные копии» на
      странице «Проекты» тоже предупредит, если последней копии больше двух
      суток.

## 2. Разработка

### 2.1. Вход по email — высокий приоритет

**Зачем.** Сейчас в проект входят по общему коду. Код можно переслать кому
угодно. Чтобы закрыть доступ одному человеку, приходится менять код для всех.
С входом по email у каждого свой адрес и роль (зритель или редактор), доступ
отзывается по одному человеку, вход запоминается на 14 дней.

**Состояние.** Код почти готов в
[PR #1](https://github.com/finger276-ops/media-digest-platform/pull/1), ветка
`claude/magical-davinci-srre4b`. PR отстал от `main` и конфликтует с ним.

**Что сделать** — объём средний:
- [ ] Подтянуть ветку к текущему `main` и разрешить конфликты.
- [ ] Переименовать миграцию PR `0007_platform_email_auth.sql` в `0008_…`:
      номер 0007 уже занят журналом правок.
- [ ] Закрыть находки независимой проверки:
  - [ ] Аналитик, вошедший по email, видит поля кодов доступа проекта. Он может
        задать код и вернуться по нему после снятия доступа. Спрятать от него
        эти поля.
  - [ ] Счётчик неверных кодов общий на адрес и не атомарный. Посторонний
        может заблокировать вход хозяину адреса, а параллельные сессии обходят
        лимит. Считать попытки в сессии вкладки.
  - [ ] По времени ответа видно, есть ли адрес в платформе: письмо шлётся
        синхронно. Отправлять письмо в фоне и отвечать одинаково.
  - [ ] `EMAIL_LOGIN_ENABLED = false` при заданных адресах владельцев снова
        открывает режим владельца всем без пароля.
  - [ ] Ответы Supabase 5xx засчитываются как неверный код. В `auth_ui`
        исключения уходят в Sentry вместе с адресом.
  - [ ] `PLATFORM_OWNER_EMAILS`, записанный массивом TOML, молча ломает вход
        владельца.
  - [ ] Из двух проектов с одинаковым названием один недоступен в выборе.
  - [ ] Таблица ограничителей попыток не чистится; «запомнить меня» работает
        без галочки.
- [ ] Полный набор тестов, пуш в `main`, зелёный CI.

**После слияния — владельцу:**
- настроить отправку писем (SMTP) в Supabase по `docs/AUTH.md` из PR;
- задать `PLATFORM_OWNER_EMAILS`;
- применить миграцию 0008;
- выдать доступы по адресам.

### 2.2. Защита на уровне базы (Row Level Security)

**Зачем.** Сейчас приложение ходит в базу служебным ключом и проверяет права
само. RLS добавляет вторую линию: даже при ошибке в коде пользователь не
прочитает чужой проект.

**Зависит от:** 2.1 — политикам нужен вошедший по email пользователь.

- [ ] Политики на таблицы проектов, периодов, данных и правок.
- [ ] Перевести чтение для пользователей с `service_role` на ключ пользователя.
- [ ] Тесты: без членства в проекте данных не видно.

### 2.3. Большие выгрузки через интерфейс

**Зачем.** Выгрузку больше ~20 000 сообщений сейчас лучше загружать через
автозагрузку. Обработка 50 000 сообщений требует около 1,5 ГБ памяти, а
приложению на Streamlit Cloud доступен примерно 1 ГБ.

**Нужно, если** такие выгрузки бывают. Объём средний.

- [ ] Замерить пик памяти на 20, 50 и 100 тыс. сообщений:
      `scripts/loadtest_pipeline.py`.
- [ ] Снизить пик: обработка частями, освобождение промежуточных таблиц,
      компактные типы колонок.
- [ ] Цель: 50 000 сообщений через «Загрузку файла» меньше чем за 1 ГБ.
      Обновить ограничение в README.

### 2.4. Ускорение по данным диагностики

**Зависит от:** 1.3 — нужны цифры с боевой платформы.

- [ ] Найти самый долгий шаг в присланных цифрах: загрузка периода из
      Supabase, склейка инфоповодов, статистика тегов, графики.
- [ ] Ускорить именно его: кеш, меньше запросов, расчёт один раз вместо
      каждой перерисовки. Замерить до и после.

## 3. Отложено или не нужно

### Отложено

- **Автозагрузка выгрузок через n8n.** Отложена владельцем. Код платформы
  готов. Остаётся настройка:
  - почтовый ящик под выгрузки Brand Analytics;
  - рассылка выгрузок из BA на этот ящик;
  - n8n (облако или свой сервер) с готовым workflow;
  - источник в разделе «Автозагрузка».

  Расписание воркера (каждые 15 минут) пока выключено, чтобы не тратить
  минуты GitHub Actions на пустую очередь. Воркер запускается вручную и по
  сигналу из n8n. Если нужна страховка на случай пропущенного сигнала,
  расписание можно вернуть, раскомментировав `schedule` в
  `.github/workflows/ingest-worker.yml`. Пошагово: `docs/AUTOMATION.md`.
- **Оповещения** о всплеске негатива или новом крупном инфоповоде в Telegram
  или на почту. Имеет смысл после автозагрузки: без неё данные не приходят
  сами.

### Не нужно

- **Разделение `platform_store.py`, `import_adapters.py`,
  `brand_metrics_ui.py`.** Замер показал, что скорость это не изменит. Сами
  модули загружаются за 0–5 мс, а время старта уходит на библиотеки pandas,
  altair и supabase, которые нужны на первой же странице. Делить стоит, только
  если в этих файлах станет неудобно работать.
- **Загрузка pptx только при выгрузке в PowerPoint.** Экономит ~0,1 с один
  раз при старте сервера. Пользователи этого не заметят.
