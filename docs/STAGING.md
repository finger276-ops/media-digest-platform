# Отдельное окружение для проверки изменений (staging)

Платформа не хранит ссылку на конкретную базу или конкретный аккаунт нигде в
коде — всё, что ей нужно, читается из секретов Streamlit Cloud или переменных
окружения (`src/platform_store.py:_secret_value`, `src/services/ai_provider.py:
_secret_value`). Это значит, что второе, полностью изолированное окружение —
не правка кода, а второй набор секретов, указывающий на второй проект
Supabase. Ничего в репозитории для этого менять не нужно.

Зачем: сейчас любое изменение (новая миграция схемы, правка конвейера
обработки, смена версии зависимости) проверяется тестами локально, а затем
сразу уходит в прод при пуше в `main`. Стейджинг — это возможность посмотреть
на изменение вживую, с настоящими данными и настоящим Streamlit-рантаймом,
прежде чем показать его аналитикам.

## Шаг 1. Второй проект Supabase

Создать новый проект в Supabase (бесплатного тарифа достаточно — объём
staging-данных небольшой). Он полностью независим от прод-проекта: свой
`SUPABASE_URL`, свой `SUPABASE_SERVICE_ROLE_KEY`, свои таблицы, свой Storage.

Применить схему — см. `sql/migrations/README.md`: выполнить
`0000_schema_migrations.sql`, затем `0001_...` и далее по порядку номеров в
SQL Editor нового проекта. Дальше на staging нужно применять точно те же
новые миграции, что появляются для прода — тем же способом, тем же порядком.

Создать приватный Storage bucket (имя — как в проде, например
`dashboard-csv`) для загружаемых файлов.

## Шаг 2. Второе Streamlit-приложение

В Streamlit Cloud завести второе приложение из того же репозитория, ветка
`main` (или отдельная ветка `staging`, если нужен более осторожный режим —
см. «Более строгий вариант» ниже). У приложения — свои Secrets:

```toml
SUPABASE_URL = "https://<staging-project>.supabase.co"
SUPABASE_SERVICE_ROLE_KEY = "service_role key staging-проекта"
SUPABASE_STORAGE_BUCKET = "dashboard-csv"
PLATFORM_ADMIN_PASSWORD = "другой пароль, не прод-пароль"
```

Остальные секреты (`ALERT_WEBHOOK_URL`, `AI_PROVIDER`/ключи ИИ и т.д.) —
по желанию: staging может работать и без них, тогда соответствующие функции
(доставка ошибок, генерация текста ИИ) просто выключены, как описано в их
разделах README.

Если используется автозагрузка (n8n), для staging нужен отдельный воркер
(`scripts/ingest_worker.py`) с переменными окружения, указывающими на
staging-проект, и отдельный workflow n8n — иначе staging и прод будут делить
одну очередь. Для одиночной проверки изменений в конвейере обработки это
обычно не нужно: достаточно ручной загрузки файла через интерфейс.

## Шаг 3. Дать себе проектовый код

Через раздел «Проекты» в staging-приложении (владелец платформы) создать
один-два тестовых проекта — можно с теми же реальными выгрузками, что уже
использовались для проверки конвейера (они не содержат ничего, кроме
публичных упоминаний бренда).

## Более строгий вариант: отдельная ветка

Если изменения должны накапливаться и проверяться пачкой, а не уходить в
прод сразу при мердже в `main`, — staging-приложение указывается на ветку
`staging`, а `main` продолжает быть тем, что видит прод. Тогда порядок:

```text
рабочая ветка → PR → main (уходит в прод при пуше)
                   → merge в staging (по готовности) → проверка на staging-приложении
```

Для платформы без выделенной команды релиз-инженерии это обычно избыточно:
локальный набор тестов (`tests/`, 23 файла на момент этого документа) уже
ловит регресс раньше, чем изменение доедет до какого-либо окружения. Отдельная
ветка staging оправдана, когда изменений много одновременно и нужно
подтверждение «на живых данных» перед тем, как показать их аналитикам —
например, перед сменой версии pandas/numpy в `requirements.txt` (см. комментарий
там же про то, что верхние границы поднимаются осознанно, после прогона тестов).

## Что проверять на staging, а не только тестами

Тесты (`tests/`) проверяют логику на синтетических и фиксированных данных —
быстро, детерминированно, без сети. Staging нужен для того, что тесты
принципиально не покрывают:

- реальный внешний вид интерфейса на боевой ширине экрана и с настоящими
  цветами/логотипом клиента;
- скорость на настоящей выгрузке (для больших объёмов — сначала
  `scripts/loadtest_pipeline.py` на синтетике, см. `README.md`, раздел про
  нагрузочный прогон; он не требует staging вовсе);
- поведение Supabase под реальной сетевой задержкой и реальными лимитами
  бесплатного/платного тарифа;
- смену версии зависимости (`requirements.txt`) в связке с реальным Streamlit
  Cloud деплоем — локальный `.venv` может отличаться от того, что Streamlit
  Cloud соберёт из чистого окружения.
