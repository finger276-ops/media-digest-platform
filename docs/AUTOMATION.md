# Автозагрузка выгрузок Brand Analytics через n8n

Документ описывает, как настроить автоматический путь «выгрузка Brand Analytics →
период в платформе» без ручной загрузки файла через интерфейс.

## Как это работает

```text
Brand Analytics            n8n                     Supabase                Платформа
────────────────           ─────────               ─────────               ─────────
отчет по расписанию  →  письмо с Excel  →  файл в Storage           →  воркер обрабатывает
на почту аналитика      забирается по IMAP  +  задача в очереди          файл и создает период
                                               platform_ingest_queue      проекта
```

Ключевая идея: n8n **не обрабатывает данные**. Он только доставляет файл в
хранилище и ставит задачу. Всю обработку делает та же логика платформы, что и при
ручной загрузке (`src/services/ingest.py`), поэтому правила Brand Analytics —
инфоповоды по колонке `Сюжет`, теги из колонок после `Обработано`, метрики
`Аудитория` / `Просмотры` — работают одинаково в обоих режимах.

Что это дает:

- один и тот же алгоритм для ручной и автоматической загрузки, без дублирования правил;
- защита от повторной загрузки одного письма (сверка по SHA-256 файла);
- видимая очередь с ошибками и кнопкой «повторить» прямо в интерфейсе платформы;
- возможность обработать очередь вручную, если воркер по расписанию еще не настроен.

## Что появилось в коде

| Файл | Назначение |
| --- | --- |
| `sql/platform_ingest_schema.sql` | Таблицы очереди и источников автозагрузки |
| `src/services/ingest.py` | Headless-пайплайн импорта (используется и интерфейсом, и воркером) |
| `src/services/ingest_queue.py` | Работа с очередью: постановка, захват, статусы, ретраи |
| `scripts/ingest_worker.py` | Воркер: разбирает очередь, создает периоды |
| `src/ingest_admin_ui.py` | Раздел «Автозагрузка» в интерфейсе |
| `.github/workflows/ingest-worker.yml` | Запуск воркера по расписанию |
| `n8n/brand-analytics-email-ingest.json` | Готовый workflow для импорта в n8n |
| `n8n/docker-compose.yml` | Self-hosted n8n одной командой |
| `requirements-worker.txt` | Зависимости воркера (без Streamlit) |

## Шаг 1. Supabase: создать таблицы

В Supabase откройте **SQL Editor → New query**, вставьте содержимое
`sql/platform_ingest_schema.sql` и выполните. Скрипт идемпотентный: повторный
запуск ничего не сломает.

Появятся:

- `platform_ingest_queue` — очередь файлов;
- `platform_ingest_sources` — маппинг «источник → проект».

Обе таблицы закрыты Row Level Security: доступ есть только у service-ключа,
с которым работают n8n и воркер.

## Шаг 2. Brand Analytics: настроить рассылку отчета

В Brand Analytics настройте автоматическую отправку выгрузки на почтовый ящик:
раздел отчетов → периодическая рассылка → формат Excel → расписание (например,
каждый понедельник в 09:00) → адрес ящика, который будет читать n8n.

Рекомендации:

- заведите отдельный почтовый ящик только под интеграцию — так письма от BA не
  смешаются с личной перепиской и фильтр не будет ошибаться;
- если проектов несколько, делайте отдельную рассылку на каждый и различайте их
  по теме письма (это станет ключом источника);
- в выгрузке обязательно должны остаться служебная колонка `Обработано` и
  колонка `Сюжет` — на них держится логика тегов и инфоповодов.

Если у вас подключен платный API выгрузки сообщений BA, шаг с почтой можно
заменить: в n8n вместо IMAP-триггера ставится Schedule Trigger + HTTP Request к
API, а дальше цепочка та же. Статистический API BA для этого не подходит — он
отдает агрегаты без текстов сообщений.

## Шаг 3. Развернуть n8n

**Вариант A — n8n Cloud.** Регистрация на n8n.io, workflow импортируется как есть.
Подходит, если не хочется администрировать сервер.

**Вариант B — self-hosted (дешевле, данные остаются у вас).** На любом VPS:

```bash
mkdir -p /opt/n8n && cd /opt/n8n
# скопировать сюда n8n/docker-compose.yml из репозитория платформы
cat > .env <<'EOF'
N8N_HOST=n8n.example.ru
N8N_BASIC_AUTH_USER=analyst
N8N_BASIC_AUTH_PASSWORD=длинный_пароль
N8N_ENCRYPTION_KEY=случайная_строка_32_символа
GENERIC_TIMEZONE=Europe/Moscow
EOF
docker compose up -d
```

Дальше поставьте перед n8n любой reverse-proxy с HTTPS (Caddy или nginx +
certbot) — вебхуки и OAuth без HTTPS работать не будут.

## Шаг 4. Импортировать workflow и подключить учетные данные

1. В n8n: **Workflows → Import from File** → `n8n/brand-analytics-email-ingest.json`.
2. Создайте учетные данные **IMAP** для почтового ящика из шага 2 и выберите их
   в узле «Почта: новое письмо».
3. Создайте учетные данные **Supabase API**:
   - Host: `https://ВАШ-ПРОЕКТ.supabase.co`
   - Service Role Secret: значение `SUPABASE_SERVICE_ROLE_KEY`

   Выберите их в узлах «Файл в Supabase Storage» и «Задача в очередь платформы».
4. Откройте узел **«Подготовка задачи»** и заполните блок `CONFIG` в начале кода:

   ```js
   supabaseUrl: 'https://ВАШ-ПРОЕКТ.supabase.co',
   bucket: 'dashboard-csv',            // тот же, что SUPABASE_STORAGE_BUCKET
   projectId: '',                      // пусто = проект определяется по sourceKey
   sourceKey: 'brand-analytics-weekly',
   sourceSystem: 'brand_analytics',
   allowedSenders: ['br-analytics.ru'],
   subjectContains: '',                // фильтр по теме, если проектов несколько
   ```

5. Активируйте workflow.

Узел «Запустить воркер сразу» выключен по умолчанию. Включите его, если не хотите
ждать планового запуска воркера: он дергает GitHub Actions сразу после загрузки
файла (нужен токен с правом `repo`).

## Шаг 5. Завести источник в платформе

В интерфейсе платформы: выберите проект → раздел **Автозагрузка** → блок
«Источники автозагрузки»:

- **Ключ источника** — ровно то же значение, что в `sourceKey` в n8n;
- **Формат выгрузки** — Brand Analytics;
- параметры алгоритма — те же ползунки, что на странице ручной загрузки.

Так проект и параметры обработки настраиваются в платформе, а n8n остается
простым «курьером» и не требует правок при добавлении новых проектов.

## Шаг 6. Запустить воркер

Есть три способа, они дополняют друг друга.

**По расписанию (основной).** В репозитории GitHub, откуда деплоится
Streamlit-приложение, откройте **Settings → Secrets and variables → Actions** и
добавьте секреты:

```text
SUPABASE_URL
SUPABASE_SERVICE_ROLE_KEY
SUPABASE_STORAGE_BUCKET
INGEST_NOTIFY_WEBHOOK   (необязательно — URL вебхука n8n для уведомлений)
```

Файл `.github/workflows/ingest-worker.yml` уже настроен: запуск каждые 15 минут,
кнопка ручного запуска и реакция на сигнал из n8n. Ограничение GitHub Actions:
расписание может задерживаться на несколько минут в часы пиковой нагрузки —
для еженедельных выгрузок это несущественно.

**Вручную из интерфейса.** Раздел «Автозагрузка» → кнопка **«Обработать очередь
сейчас»**. Удобно для первого теста и когда выгрузка нужна немедленно.

**С любого сервера.** Если есть VPS с n8n, воркер можно запускать там же по cron:

```bash
export SUPABASE_URL=... SUPABASE_SERVICE_ROLE_KEY=... SUPABASE_STORAGE_BUCKET=...
python scripts/ingest_worker.py --max-tasks 10 --verbose
```

## Шаг 7. Проверить

1. Отправьте на интеграционный ящик письмо с тестовой выгрузкой BA (можно
   переслать последнее письмо от Brand Analytics).
2. В n8n: **Executions** — выполнение должно пройти по всей цепочке.
3. В платформе: раздел **Автозагрузка** — задача со статусом «В очереди».
4. Нажмите «Обработать очередь сейчас» (или дождитесь воркера).
5. Статус меняется на «Загружено», а в разделе **Дашборд** появляется новый
   период с автоматическим названием вида `24.04.2026–30.04.2026`.

## Диагностика

| Симптом | Причина и что делать |
| --- | --- |
| В n8n выполнение зеленое, но задачи в платформе нет | Сработала защита от дублей: файл с таким SHA-256 уже загружался в этот проект. Это нормальное поведение при повторной отправке письма |
| Задача «Ошибка»: «Источник не найден» | Ключ источника в n8n (`sourceKey`) не совпадает с ключом в разделе «Автозагрузка» либо источник выключен |
| Задача «Ошибка»: «Не удалось прочитать файл выгрузки» | Excel не содержит распознаваемой таблицы сообщений. Откройте файл: нужны колонки с датой, текстом, ссылкой/источником. Пустые листы платформа пропускает, лист «Сообщения» берет приоритетно |
| Задача «Ошибка»: «Файл не найден в Supabase Storage» | Не совпал bucket в n8n и в секретах платформы, либо загрузка файла в Storage упала раньше — проверьте узел «Файл в Supabase Storage» |
| Задача висит в «Обрабатывается» | Предыдущий запуск воркера прервался. Через 45 минут задача автоматически вернется в очередь; можно вернуть сразу кнопкой «Повторить обработку» |
| Период создался, но метрики нулевые | В выгрузке нет колонок `Аудитория` / `Просмотры` либо они пришли текстом с нестандартными символами. Проверьте исходный файл |
| Периоды дублируются | Название периода приходит разное при одинаковых данных. Оставьте поле периода пустым — платформа назовет период по датам сообщений, и повторная обработка перезапишет тот же период |

Логи воркера: в GitHub Actions в шаге «Обработать очередь» видно, какие задачи
взяты, сколько сообщений и инфоповодов получилось, и полный текст ошибок.

## Безопасность

- `service_role`-ключ Supabase дает полный доступ к базе. Он должен лежать только
  в учетных данных n8n и в секретах GitHub Actions — не в коде workflow и не в
  переписке.
- Таблицы очереди закрыты RLS, поэтому анонимный ключ их не увидит.
- Отдельный почтовый ящик под интеграцию снижает риск случайной обработки чужого
  вложения: в фильтре отправителя оставьте только домены Brand Analytics.
- Если нужна полная изоляция, заведите под платформу отдельный Supabase-проект и
  отдельный bucket (`digest-platform-files`).

## Несколько проектов

Схема масштабируется без правок кода:

1. В BA — отдельная рассылка на тот же ящик, но с узнаваемой темой письма.
2. В n8n — копия workflow, где в `CONFIG` меняются `sourceKey` и
   `subjectContains` (или один workflow с ветвлением по теме письма).
3. В платформе — новый источник с этим `sourceKey`, привязанный к нужному проекту.
